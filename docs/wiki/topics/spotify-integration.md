# Spotify Integration

## Summary [coverage: high — 4 sources]

Spotify is integrated into Cockpit as a parallel audio source to MP3 playback. Authentication is OAuth 2.0 PKCE with a hardcoded client ID and `127.0.0.1` redirect (not `localhost`), via a temp HTTP server bound to `127.0.0.1`. Tokens are persisted in SQLite (plaintext, in `userData/visual.db`). As of session 24 (2026-04-06), the **Web Playback SDK has been removed entirely** because it requires Widevine/EME and a castlabs Electron build. It is replaced by Spotify Web API polling (`GET /v1/me/player` every 2 seconds) for playback state and Web API commands (`PUT/POST /v1/me/player/*`) for control — playing on the user's existing active Spotify device. The earlier naudiodon WASAPI approach was abandoned; on 2026-04-07 its references were removed from `apps/desktop/package.json` (`postinstall` and `rebuild:native`) because installs were repeatedly trying to rebuild a module that wasn't in `node_modules`. **Visualizer audio reactivity to Spotify is now implemented (2026-04-07, session 25b).** `SpotifyPlayerAudio.ts` was rewritten: the session-25 silent-oscillator stub was removed and replaced with a renderer-side `getDisplayMedia({ video: true, audio: true })` capture. Video tracks are stopped and removed immediately; the audio track is wired into the existing Cockpit `AnalyserNode` via a `MediaStreamAudioSourceNode`. The analyser is deliberately **not** connected to `ctx.destination` to avoid speaker feedback. A new "Enable Audio Reactivity" toolbar button in `SpotifyBrowser.tsx` is the user-gesture entrypoint (Electron disallows `getDisplayMedia` without a gesture), and `CockpitApp.tsx`'s OAuth auto-reconnect path no longer calls `startLoopback()` because the gesture chain is not preserved across the OAuth callback. Caveat: the Electron `setDisplayMediaRequestHandler({ audio: 'loopback' })` hook captures **all** system audio, not Spotify-only — UI text reflects this. Also on 2026-04-07, `SpotifyPlayerAPI.ts` was updated to `console.error` status + statusText on non-OK responses so auth failures (401/403/429) are no longer silent, and `SpotifyBrowser.tsx` surfaces an explicit empty-playlist hint telling the user to check the console. Later the same day, a stale-scope bug on a collaborator's machine (where `/v1/me/playlists` returned playlists with `tracks === undefined` and `/v1/playlists/{id}/tracks` returned 403) prompted bumping `REQUIRED_SCOPE_VERSION` in `electron/spotify-auth.ts:11` from `'2'` to `'3'`; existing tokens are now cleared on next launch via `checkAndInvalidateScopeChange()`, forcing re-OAuth with the full `playlist-read-private` / `playlist-read-collaborative` scope set. The `SpotifyPlayerAPI.ts` `console.warn` also gained a `typeof p.tracks` dump so undefined/null/`{total:0}` cases are distinguishable in logs, and `SpotifyBrowser.tsx` now renders a `sp-reconnect-banner` when `playlists.length > 0` but every playlist has `trackCount === 0` — catching the stale-scope case in the UI instead of showing an empty list.

## Decisions & Rationale [coverage: high — 6 sources]

- **Scope version bump to `'3'` + stale-scope UI banner (2026-04-07).** A collaborator's machine had tokens granted under an older scope set that no longer included the full playlist-read scopes, and Spotify's API responded with playlists whose `tracks` field was undefined and per-playlist track fetches returning 403. Rather than trying to detect and refresh in place, the fix bumps `REQUIRED_SCOPE_VERSION` in `electron/spotify-auth.ts:11` from `'2'` to `'3'`, which makes `checkAndInvalidateScopeChange()` wipe the cached token on next launch and force a clean re-OAuth. Complementary UI change: `SpotifyBrowser.tsx` detects the "playlists returned but every one has `trackCount === 0`" shape and renders a `sp-reconnect-banner` prompting the user to disconnect/reconnect, so users on pre-bump tokens aren't stranded with a silently empty UI.
- **Visualizer loopback via `getDisplayMedia`, not a custom PCM pipe (2026-04-07, session 25b).** Rather than writing a `ScriptProcessorNode`/`AudioWorklet` that pulls PCM chunks from the IPC queue (the session-24 plan that never landed), `SpotifyPlayerAudio.ts` now calls `getDisplayMedia({ video: true, audio: true })` and pipes the captured audio track straight into the existing AnalyserNode via `MediaStreamAudioSourceNode`. Video tracks are stopped/removed immediately on the returned stream. The analyser is deliberately not connected to `ctx.destination` — connecting it would route captured system audio back through the speakers and create a feedback loop. This approach works because Electron 29's `setDisplayMediaRequestHandler({ audio: 'loopback' })` hook (from session 24) makes `getDisplayMedia` return a system-loopback stream with no additional native dependencies.
- **"Enable Audio Reactivity" button instead of auto-start (2026-04-07, session 25b).** `getDisplayMedia` requires an active user-gesture chain in Electron. The OAuth auto-reconnect path in `CockpitApp.tsx` previously called `startLoopback()` there, which threw `NotAllowedError` because the gesture chain is not preserved across the OAuth HTTP callback. The fix: a "Enable Audio Reactivity" toolbar button in `SpotifyBrowser` that the user clicks directly. `handleSpotifyConnected` still attempts `startLoopback()` best-effort (commented) but the button is the reliable fallback.
- **Loopback returns boolean, swallows failures (2026-04-07).** `startLoopback()` wraps the `getDisplayMedia` + stream-wiring in try/catch and returns `false` on failure (no audio tracks on macOS/Linux, `NotAllowedError` without gesture, etc.) instead of throwing. Rationale: loopback is Windows-only in practice and the UI needs a stable signal to flip the button label without crashing the renderer.
- **Surface API errors, never fail silently (2026-04-07).** `fetchPlaylists()` and `fetchPlaylistTracks()` now `console.error` `response.status` + `statusText` before returning `[]`, and `SpotifyBrowser`'s empty state (when `isConnected`) tells the user: "No playlists loaded. Check console for errors or try disconnecting and reconnecting Spotify." The previous behavior silently swallowed 401/403/429 responses, which made token/scope/rate-limit issues undiagnosable from the UI.
- **Drop naudiodon in favor of Electron native loopback hook (2026-04-07).** naudiodon required MSVC Build Tools and a native compile step, and kept failing rebuild attempts during install. Electron 29's `setDisplayMediaRequestHandler({ audio: 'loopback' })` captures system audio output with no native dependency. naudiodon was removed from `package.json` `postinstall` and `rebuild:native` on 2026-04-07; `better-sqlite3` rebuild remains.
- **Drop Web Playback SDK entirely (session 24, 2026-04-06).** SDK requires Widevine CDM via castlabs `electron-releases`. Replaced with Web API polling + system-audio loopback. Standard `electron@^29.4.6` restored.
- **Hardcode client ID, use `127.0.0.1` redirect (session 16, 2026-04-05).** One-click login. `localhost` was changed to `127.0.0.1` because the Spotify dashboard now requires it. Temp HTTP server bound explicitly to `127.0.0.1`.
- **Decouple "has token" from "SDK ready" (session 20, 2026-04-05).** Added `markTokenValid(hasToken: boolean)` so `isConnected` is set without waiting for SDK. The browser then renders as soon as a token exists. (Now obsolete with SDK removed but the decoupling pattern remains.)
- **Scope invalidation on startup (session 23; bumped to v3 on 2026-04-07).** `checkAndInvalidateScopeChange()` stores current scope string in DB and clears tokens on startup if scope changed. Prevents stale tokens from causing silent 403s. Required scopes include `playlist-read-private`, `playlist-read-collaborative`, `user-read-playback-state`, `user-modify-playback-state`. `REQUIRED_SCOPE_VERSION` was bumped `'2'` → `'3'` on 2026-04-07 to force reissue after collaborator tokens surfaced stale-scope 403s on playlist-track fetches.
- **Token security model (planned).** DB gitignored; installer excludes `userData`; first-time use prompts OAuth. Per-user, per-machine, no server, scales to public distribution. Disconnect clears the token.

## Patterns & Gotchas [coverage: high — 5 sources]

- **Silent `[]` from `fetchPlaylists` = auth/scope/rate-limit failure.** The function now logs `response.status` + `statusText` — check the console before assuming an empty account. Don't treat an empty return as "no data".
- **`playlists.length > 0` but every `trackCount === 0` = stale scope, not empty playlists.** This was the 2026-04-07 collaborator bug: Spotify happily returned the playlist list but the `tracks` field was undefined on each, so track counts defaulted to 0 across the board. If you see this shape, the token was granted under an older scope version — bump `REQUIRED_SCOPE_VERSION` or have the user disconnect/reconnect. The `sp-reconnect-banner` in `SpotifyBrowser.tsx` now catches this automatically.
- **Log `typeof p.tracks`, not just the count.** `SpotifyPlayerAPI.ts`'s warn path now dumps `typeof p.tracks` so `undefined` vs `null` vs `{ total: 0 }` are distinguishable at a glance. Raw count alone can't tell you whether the scope is wrong or the playlist is genuinely empty.
- **Loopback captures all system audio, not just Spotify.** This is inherent to Electron's `setDisplayMediaRequestHandler({ audio: 'loopback' })`. Don't word the UI or docs as "Spotify-only audio reactivity" — if the user has YouTube playing in the background, the visualizer will react to that too. The current `SpotifyBrowser` button just says "Enable Audio Reactivity".
- **`getDisplayMedia` requires a user gesture in Electron.** Calling `startLoopback()` from a non-gesture code path (OAuth callback, `useEffect`, auto-reconnect, `setTimeout`) throws `NotAllowedError`. Always tie activation to an explicit button click. `CockpitApp.tsx`'s auto-reconnect path learned this the hard way.
- **Don't connect the AnalyserNode to `ctx.destination`.** The loopback stream IS the system output, so routing it back creates a feedback loop. The analyser is a pure sink for the visualizer — it only reads frequency/waveform data, never plays back.
- **403s on play/pause/skip = missing scopes.** Always include the playback-control scopes.
- **Auto-reconnect race.** `SpotifyPlayer.markTokenValid(true)` must be called *before* `init()` so `SpotifyBrowser` sees `isConnected` immediately.
- **`fetchPlaylistTracks` uses `limit=50` per API spec.** Earlier "0 tracks" bug was a defensive `(p.tracks?.total as number) ?? 0` typing issue.
- **Artist separator is ` / ` not `, `.** Applied in both API and (formerly) SDK paths.
- **Audio routing must extract to its own module.** `SpotifyPlayerAudio.ts` exists because the audio graph needs to be a singleton independent of React lifecycle.
- **CSP gotcha (now obsolete).** SDK previously needed `https://sdk.scdn.co` in `script-src`. With SDK removed, this can stay or go.
- **Promise rejection on hub autoplay.** Use `audio.play().catch(() => {})` not `try/catch` — the rejection from "play() interrupted by pause()" is async (session 25).

## Open Threads [coverage: medium — 2 sources]

- Manual test on Windows: connect Spotify → play a track → click "Enable Audio Reactivity" → verify the visualizer reacts. Verify that pausing Spotify produces a flat waveform and that other system audio (YouTube, etc.) also drives the visualizer (expected, document if surprising).
